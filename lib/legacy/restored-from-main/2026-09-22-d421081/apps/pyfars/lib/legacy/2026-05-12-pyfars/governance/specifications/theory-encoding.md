# §1 Abstract

A **theory** in the FARS substrate is a substrate-resident predication fibration: a triple $(\mathbf{L}, \mathcal{C}, E)$ where $\mathbf{L}$ is the four-valued bilattice $\mathbf{FOUR}$, $\mathcal{C}$ is the predicate category (objects = predicates, morphisms = four canonical generator classes), and $E$ is the entity set realized as the theory's directory of `.md` files.
"Substrate-resident" means every predicate $q \in \mathrm{Ob}(\mathcal{C})$ is itself a file in $E$, and every predication in the fibration $\mathcal{E}$ is expressible as a `(file, frontmatter-key, frontmatter-value)` triple.

A `(file, key, value)` triple is a **predication** $(e_1, q, e_2)$: entity $e_1$ is the file, predicate $q$ is named by the key, entity $e_2$ is the value.
Asserting the predication in frontmatter fixes its bilattice value to $\mathbf{t}$.
The frontmatter of a file is the set of $\mathbf{t}$-valued predications asserted for that entity.

A theory is **well-formed** when every predicate object in $\mathcal{C}$ is substrate-resident and every predication in $\mathcal{E}$ is type-correct with respect to the four canonical generator classes.
This specification derives the normative requirements for that well-formedness directly from the predication-fibration definition.

# §3 Conformance

Normative language follows RFC 2119: MUST, MUST NOT, SHOULD, SHOULD NOT, MAY.

A **conformant theory** is a directory tree satisfying all MUST requirements in §5.
A **conformant FARS realization** loads the predicate category by reading every file in `transformers/` (and inherited theory `transformers/`), constructs $\mathcal{C}$, and validates every entity's frontmatter against $\mathcal{C}$'s typing structure.

# §4 Terminology

**Theory** $(\mathbf{FOUR}, \mathcal{C}, E)$.
A substrate-resident predication fibration.
The entity set $E$ is the theory's `.md` file collection.
The predicate category $\mathcal{C}$ has the theory's transformer entities as its object set $\mathrm{Ob}(\mathcal{C})$.

**Predicate / transformer.** An object $q \in \mathrm{Ob}(\mathcal{C})$.
In the substrate: a file in `transformers/` with `type: transformer`.
In the frontmatter of an entity file: the **key** of a `(file, key, value)` triple.

**Entity.** An element $e \in E$: any `.md` file in the theory.
Every entity carries a `has-type` predication identifying its type-classifier.

**Type-classifier / structure.** An entity $T \in E$ in the image of `has-type`: some entity $e$ has $(e, \mathtt{has\text{-}type}, T)$ at $\mathbf{t}$.
In the substrate: a file in `structures/` with `type: structure`.
Type-classifiers are themselves entities and must be type-classified: `(T, has-type, structure)`.

**Predication.** A triple $(e_1, q, e_2) \in E \times \mathrm{Ob}(\mathcal{C}) \times E$.
Encoded in the substrate as the frontmatter entry `q: e₂` in file `e₁`.
The bilattice value is $\mathbf{t}$ for asserted predications; absence is $\bot$.
The fibration $\mathcal{E}_q \cong \mathbf{FOUR}^{\bowtie E \times E}$ assigns a bilattice value to every $(e_1, q, e_2)$ triple.

**Subject-type / object-type of a predicate.** Every predicate $q$ has two type-classifiers determined by the four canonical generators of $\mathcal{C}$: its **subject-type** $S(q)$ (the type-classifier that entities appearing as $e_1$ in $(e_1, q, -)$ must satisfy) and its **object-type** $O(q)$ (the type-classifier for entities appearing as $e_2$).
These are encoded as the predications $(q, \mathtt{has\text{-}subject\text{-}type}, S(q))$ and $(q, \mathtt{has\text{-}object\text{-}type}, O(q))$ on the predicate entity itself.

**Four canonical morphism classes.** Per [predicate-category](../../../../../theories/theories/humanities/theories/math/theories/categories/theories/predication-categories/objects/predicate-category.md) and [predication-fibration](../../../../../theories/theories/humanities/theories/math/theories/categories/theories/predication-categories/objects/predication-fibration.md): the only morphisms in $\mathcal{C}$ are generated by predicate-specialization, predicate-converse, predicate-subject-projection, and predicate-object-projection.
These four classes are the only valid predications on predicate entities.

# §5 Requirements

## §5.1 Theory index

R1.
A theory directory MUST contain an `_index.md` with `type: theory-index` in its frontmatter.

R2.
The `_index.md` MUST carry `derives-methods-from-theory:` naming zero or more parent theory paths.
The parent theories' predicate categories are inherited: $\mathrm{Ob}(\mathcal{C}) = \mathrm{Ob}(\mathcal{C}_{\mathrm{local}}) \cup \bigcup_{\mathrm{parent}} \mathrm{Ob}(\mathcal{C}_{\mathrm{parent}})$.

## §5.2 Predicate entities (transformer records)

R3.
Every object $q \in \mathrm{Ob}(\mathcal{C})$ MUST be a file in the theory's `transformers/` directory (or an ancestor theory's `transformers/`).

R4.
Every predicate entity MUST carry `(q, has-type, transformer)` — equivalently, `type: transformer` in its frontmatter.

R5.
Every predicate entity MUST carry `(q, has-subject-type, S(q))` and `(q, has-object-type, O(q))`, where $S(q)$ and $O(q)$ are type-classifier entities in $E$.
These predications correspond to the subject-projection and object-projection generator classes of $\mathcal{C}$.

R6.
A predicate entity MAY carry `(q, specializes, p)` where $p$ is a predicate in $\mathrm{Ob}(\mathcal{C})$.
This encodes a specialization morphism $q \to p$ in $\mathcal{C}$.
Subject-type and object-type are inherited from $p$ when not overridden.

R7.
A predicate entity MAY carry `(q, converse, q')` where $q'$ is a predicate in $\mathrm{Ob}(\mathcal{C})$.
This encodes the converse-generator morphism.
Symmetry: if $(q, \mathtt{converse}, q')$ is asserted, then $(q', \mathtt{converse}, q)$ MUST also hold.

R8.
Predicate entities MUST NOT carry frontmatter keys other than those in R4–R7, plus the keys whose predicates have subject-type `transformer` in the accumulated $\mathcal{C}$.
No invented metadata fields are admissible.

## §5.3 Type-classifier entities (structure records)

R9.
Every type-classifier entity MUST be a file in the theory's `structures/` directory (or an ancestor theory's `structures/`).

R10.
Every type-classifier entity MUST carry `(T, has-type, structure)` — equivalently, `type: structure` in its frontmatter.

R11.
Type-classifier entities are subject to the same predication discipline as all entities (§5.4–§5.5).
The valid predications on a type-classifier entity are those whose predicate $q$ has $S(q) = \mathtt{structure}$ or $S(q) = \mathtt{entity}$ (universal domain).

## §5.4 Entity predication discipline

R12.
Every entity $e \in E$ MUST carry exactly one `(e, has-type, T)` predication at $\mathbf{t}$, where $T$ is a substrate-resident type-classifier.
Multiple `type:` keys in a single file MUST be treated as a $\mathbf{\top}$ (paraconsistent) predication and surfaced as a validation error.

R13.
Every frontmatter key in any entity file MUST name a predicate $q \in \mathrm{Ob}(\mathcal{C})$.
A key that does not name a substrate-resident predicate entity is an **invalid predication** and MUST be surfaced as a validation error.

R14.
For every predication $(e_1, q, e_2)$ in an entity's frontmatter: the type of $e_1$ MUST be a sub-type of $S(q)$ (or $S(q) = \mathtt{entity}$), and the type of $e_2$ MUST be a sub-type of $O(q)$.
Type violations MUST be surfaced as validation errors.

R15.
A predication $(e_1, q, e_2)$ where $e_2$ is a primitive literal (string, integer, timestamp, bilattice-value) is valid when $O(q)$ is a designated primitive type-classifier (`string`, `integer`, `iso8601-timestamp`, `bilattice-value`, `path-reference`).
These primitive type-classifiers are substrate-resident structure entities in the root theory.

## §5.5 Self-description

R16.
The predicates `has-type`, `has-subject-type`, `has-object-type`, `specializes`, and `converse` MUST be substrate-resident predicate entities in the accumulated $\mathcal{C}$.

R17.
These predicates are subject to R4–R8 without exception.
Specifically: - `has-type` has $S(\mathtt{has\text{-}type}) = \mathtt{entity}$ and $O(\mathtt{has\text{-}type}) = \mathtt{type\text{-}classifier}$. - `has-subject-type` has $S(\mathtt{has\text{-}subject\text{-}type}) = \mathtt{transformer}$ and $O(\mathtt{has\text{-}subject\text{-}type}) = \mathtt{type\text{-}classifier}$. - `has-object-type` has $S(\mathtt{has\text{-}object\text{-}type}) = \mathtt{transformer}$ and $O(\mathtt{has\text{-}object\text{-}type}) = \mathtt{type\text{-}classifier}$. - `specializes` has $S(\mathtt{specializes}) = \mathtt{transformer}$ and $O(\mathtt{specializes}) = \mathtt{transformer}$. - `converse` has $S(\mathtt{converse}) = \mathtt{transformer}$ and $O(\mathtt{converse}) = \mathtt{transformer}$.

No special cases.
The validity of these predications on the predicate entities themselves is established by their own conformance to R4–R7.

R18.
The type-classifiers `entity`, `transformer`, `structure`, and the primitive type-classifiers MUST be substrate-resident structure entities in the root theory or inherited from it.

# §6 Acceptance criteria

AC1.
The predicate category $\mathcal{C}$ is constructible: walking `derives-methods-from-theory` chains yields a set of predicate entities (transformer files) with no name collisions and no cycles in `specializes`.

AC2.
Every predicate entity carries `has-subject-type` and `has-object-type` predications naming substrate-resident type-classifiers.

AC3.
Every entity file's `type:` value names a substrate-resident type-classifier.

AC4.
Every non-`type:` frontmatter key in every entity file names a predicate in $\mathrm{Ob}(\mathcal{C})$ whose `has-subject-type` is compatible with the entity's type.

AC5.
Every frontmatter value names an entity whose type is compatible with the predicate's `has-object-type`, or is a primitive literal compatible with the predicate's primitive codomain type-classifier.

AC6.
The five self-describing predicates (R16) are substrate-resident and themselves pass AC2–AC5.

# §7 Non-normative example

*Not normative.*

A theory encoding the predicate `depends-on` would contain a file `transformers/depends-on.md` with:

```yaml
type: transformer
has-subject-type: entity
has-object-type: entity
```

An entity `objects/foo.md` carrying `depends-on: bar` would be valid iff `bar` resolves to an entity in $E$, and `entity` is compatible with both the subject-type and the declared type of `foo.md`.

By contrast, a file `structures/theorem.md` containing the key `proof-method:` is invalid unless `proof-method` is a substrate-resident predicate whose `has-subject-type` includes `theorem` — it cannot be an invented metadata label.

# §8 What this specification does not decide

- **The root theory's location.** Which theory in the lineage is the root (defining primitive type-classifiers and the five self-describing predicates) is a deployment decision, not this spec's.
- **Primitive type coercion and reference resolution.** How slug-references resolve to paths, and how the substrate disambiguates same-slug entities, is the reference-resolution spec's domain.
- **Converse uniqueness.** Whether every predicate must have a named converse, or whether unnamed converses are admissible, is deferred.
- **Higher-arity predicates.** This spec defines binary predicates $(e_1, q, e_2)$.
  N-ary predicates require a separate treatment of how the entity-pair index $E \times E$ generalizes.
