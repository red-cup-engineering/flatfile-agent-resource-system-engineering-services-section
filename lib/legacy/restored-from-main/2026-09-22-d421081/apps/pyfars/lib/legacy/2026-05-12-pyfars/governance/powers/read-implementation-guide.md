The developer may read any entity under `work/implementation/` without incurring a duty and without the passive party having any claim against this reading.
A Hohfeldian privilege: the developer has a liberty; the substrate has a no-right.

This privilege is the epistemic precondition for `write-pyfars-source`.
The `derive-from-theory-before-planning` duty requires the developer to exercise this privilege before writing code — the privilege's existence is what makes the duty's required-action non-burdensome: the developer is not being asked to do something it has no standing to do.

## What the privilege guarantees

No gating on reading.
The developer does not need the records officer's permission or the theory-derivation-officer's permission to read an implementation guide.
The guide was written *for* the developer; the privilege reflects this: the developer is its primary intended reader.

## The privilege does not cover modification

The developer may read implementation guides but not write them.
Writing an implementation guide is `write-implementation-guide`, held by the theory-derivation-officer.
If the developer reads a guide and finds it incorrect or insufficient, the response is to file a triage note (via the XO's intake) flagging the gap — not to edit the guide directly.
